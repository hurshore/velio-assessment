# Shared API contract, version 1

Current implementation and planned follow-up contracts for PLANS.md §2.3–2.6 and §4.1. Health/readiness, organic demo identities, host activity creation/inspection, and validated activity-view ingestion are implemented. Seat booking/recovery and the transactional outbox writer are also implemented. Invitations and product metrics remain in subsequent tickets; sections labelled planned describe those future boundaries. Changes to planned decisions must be recorded in PLANS.md §6.

## HTTP boundary

JSON under `/api`. Successful responses: `{ "data": <payload>, "requestId": "<server UUID>" }`. Errors: `{ "error": { "code": "NOT_FOUND", "message": "...", "retryable": false }, "requestId": "<server UUID>" }`. The server emits the same UUID in `X-Request-Id`; clients display safe messages and keep this reference for diagnosis. No stack traces or dependency credentials are returned. Dates are UTC ISO-8601 strings; activity display includes its IANA timezone. Monetary amounts are integer minor units plus currency.

- `GET /api/health`: 200, data `{ "status": "ok", "service": "velio-api" }`; process liveness only.
- `GET /api/ready`: checks PostgreSQL `SELECT 1` and Redis `PING` on each request; 200 data `{ "status": "ok", "dependencies": { "postgres": "ok", "redis": "ok" } }`. A dependency failure returns 503 with code `DEPENDENCIES_UNAVAILABLE`, retryable true. Readiness probes are bounded; liveness stays available during outages.
- Unknown paths: 404 `NOT_FOUND`. Invalid JSON: 400 `INVALID_JSON`. Oversized JSON: 413 `PAYLOAD_TOO_LARGE`. Unexpected errors: 500 `INTERNAL_ERROR`, retryable true.

Initial domain error vocabulary: `INVALID_REQUEST` (400), `IDENTITY_REQUIRED` (401), `RECIPIENT_MISMATCH`/`INVITE_NOT_ALLOWED` (403), `NOT_FOUND`/`INVALID_INVITE` (404), `SOLD_OUT`/`ALREADY_REDEEMED`/`IDEMPOTENCY_CONFLICT` (409), `INVITE_EXPIRED`/`ACTIVITY_STARTED` (410), and `TEMPORARILY_UNAVAILABLE` (503). Clients must inspect codes rather than parse messages. Domain tickets finalize endpoint payloads against the canonical plan; these names do not claim those routes exist.

## Booking writes and identity

Demo identity is explicitly selected and persisted; it is not production authentication. Booking writes carry the selected actor and `Idempotency-Key` (opaque UUID retained across uncertain outcomes). The server scopes keys by actor/operation and fingerprints payloads. Same key/same intent returns the committed result; changed payload returns `IDEMPOTENCY_MISMATCH`. A retry or own-booking lookup recovers confirmation before showing failure. Different keys still consume only one seat per user/activity. A transaction rollback leaves the intent retryable. Booking responses contain the committed booking, plan membership, price snapshot, and authoritative availability.

## Invitations and acquisition

`rail` is exactly `vouch` or `public`. Vouches are bound to one intended demo contact; public links allow distinct guests while capacity exists. Neither reserves seats. Codes are opaque server-issued values. Requests supply a code, never fabricated inviter, rail, root, or generation. Public previews exclude contacts. Expiry is the earlier of 24 hours after creation and activity start. Existing-booking recovery preserves its original attribution.

Signup generation is immutable product acquisition history: organic 0, new invite signup = inviter generation + 1, frozen parent/root and acquisition rail. Returning users retain signup history; later booking attribution is separate. Invites snapshot the inviter's signup ancestry.

## Events and guest journeys

Schema version `1`. Event envelope: `id` (UUID), `schemaVersion`, `name`, `occurredAt` (UTC), `source` (`server`/`client`), `platform` (`web`/`mobile`), optional `actorId`/persistent anonymous `journeyId`, relevant entity IDs, authoritative `rail`/`generation`, experiment version/assignment, outcome/reason, and synthetic marker. Optional fields are omitted when unknown, never invented. IDs deduplicate ingestion.

Persist a random guest journey ID before rendering an invite; retain it across opens, identity creation, and uncertain claims. `invite_opened` means a human rendered the preview, including full/expired states; link-preview GETs are not opens. Server success events persist atomically with their domain changes; attempt/failure telemetry survives rollback. No contact data in analytics. Event names and metric windows follow PLANS.md §4.1–4.2.

## Versioned availability

Snapshot: `{ "eventId": "<UUID>", "activityId": "...", "version": 1, "capacity": 2, "confirmedCount": 1, "remainingSeats": 1 }`. Versions increase with committed changes; counts come from PostgreSQL. Redis publication uses the durable outbox. Clients ignore duplicate/older versions, subscribe with snapshot recovery, reconcile periodically, and refresh on foreground/reconnect. ACK `{ "activityId": "...", "version": 1, "eventId": "..." }` only after visible application. Cached/offline capacity is labelled stale and cannot enable a claim. The implemented WebSocket endpoint and live delivery storage are described in the #7 slice below.

## CORS and readiness validation

The allowed WEB_ORIGIN is one validated HTTP(S) origin, normalized to its browser form. Preflight permits GET/POST/OPTIONS and Content-Type, Idempotency-Key, and X-Demo-Actor-Id (the planned demo identity header). Unapproved origins, methods, or headers receive 403 CORS_REQUEST_DENIED; unapproved origins are never reflected. Responses vary by Origin and preflight request method/headers. No cookie-credential CORS mode is enabled.

Both clients require an object envelope with a nonempty string request reference. A 200 readiness response must have status=ok and both dependencies ok; an error response must have a nonempty string code/message and boolean retryability. Unknown valid codes use safe connection guidance. Malformed/non-JSON responses show “The API returned an unexpected response. Please retry.” and never render unchecked reference fields. [Shared fixtures](readiness-fixtures.json) exercise error/malformed payload parity in both UI suites; request references are treated as opaque strings, while the API generates UUIDs.

## Host activity slice (#2)

- `POST /api/identities`: `{displayName, journeyId, platform, synthetic?, test?}`. `journeyId` is a UUID; platform is `web` or `mobile`; markers are booleans defaulting to false. Returns 201 `{id, displayName, generation: 0, acquisitionParentId: null, acquisitionRootId: id, synthetic, test}`. Signup ancestry and the server `identity_created` event persist atomically. Unknown fields (including invented referral ancestry) are rejected.
- `GET /api/identities`: all selectable demo identities, ordered by creation. This deliberately public demo directory exposes display names and ancestry IDs, never contact data. `GET /api/identities/:id` restores the same identity or returns `NOT_FOUND`.
- `POST /api/activities`: requires an existing `X-Demo-Actor-Id`. Body `{title, description, meetingLocation, startsAt, timezone, capacity, priceMinor, currency}`. Trimmed text limits are 120/2000/300 characters. `startsAt` is a valid absolute ISO calendar timestamp with seconds and `Z` or an explicit offset, normalized to UTC. `timezone` is an IANA zone (`UTC` also accepted). Input is resolved case-insensitively to a name supported by PostgreSQL and its display-timezone constraint, then checked by the backend Intl formatter before insertion. For example, `africa/lagos` is stored and returned as `Africa/Lagos`; unsupported zones return 400 `INVALID_REQUEST`, retryable false, with timezone guidance. Capacity is an integer in 1…2147483647; price is an integer in 0…2147483647 minor units; currency is an explicit uppercase three-letter code. This slice allows inspection of past activities too; booking eligibility is #3. Unknown fields are rejected. Returns 201 authoritative details.
- `GET /api/activities`: discovery list with `{id, hostId, title, description, meetingLocation, startsAt, timezone, status, capacity, confirmedCount, remainingSeats, priceMinor, currency, version, planId}`. `GET /api/activities/:id` adds `participants: [{id, displayName}]` from confirmed booking rows, excluding contacts. New activities have scheduled status, version 1, zero confirmed count and capacity remaining. PostgreSQL creates one plan per activity; host creation creates no booking.
- `POST /api/events`: accepts only schema-1 client `activity_viewed` in this slice. Required `{id, schemaVersion: 1, name: 'activity_viewed', source: 'client', occurredAt, platform, activityId}`; optional `{actorId, journeyId, planId, synthetic, test}`. At least selected actor or journey UUID is required. Any actor must match `X-Demo-Actor-Id` and exist. Activity must exist; supplied plan must belong to it. The server derives plan/generation and inherits selected-identity and activity-host markers, including anonymous seed views (a client cannot clear them). Invalid source/name, fabricated rail/generation, unknown fields, malformed timestamps/UUIDs and non-boolean markers are rejected. Returns 202 `{id, accepted: true}` for a new event, or `accepted: false` for an existing event ID, leaving the first record untouched. Only successful ingestion means durable receipt. Once details render, the web captures the event ID, actor, activity/plan, journey and occurrence time. App-owned delivery continues through ordinary in-app navigation and identity changes; every attempt is bounded to eight seconds. Failures remain visible in the app with a retry using the original ID, payload and actor header; server deduplication handles uncertain receipts.

Both boundaries validate inputs; PostgreSQL constraints additionally protect capacity, count bounds, timezone, price and currency. Runtime grants allow identity display-name updates, but no ancestry update/user deletion, signup-attribution update/delete, event update/delete, plan mutation or booking writes. Migration credentials alone run seeds. The read-only confirmed booking schema is established here; #3 adds the authoritative booking transaction, idempotency, attribution and outbox, plus its narrowly required runtime grants.

Web storage keys are versioned (`velio.actor.v1`, `velio.journey.v1`). Identities and activities load independently. Activity creation has a reversible pending list row; it never changes availability counts optimistically. A rejected request removes that row and preserves the form. A transport failure can occur after commit, so the UI asks users to refresh before retrying creation; activity-creation idempotency is not promised. Start input uses the device timezone, explicitly labelled, with both a selected display-zone preview and a UTC instant. Availability/participants are snapshots in #2; live updates belong to the later live ticket. Rendered-view delivery state is retained in memory for the current app session. Browser refresh/closure delivery is best effort and can lose pending or failed events; a persistent offline telemetry queue is outside this correction.

## Seat booking slice (#3)

- `POST /api/activities/:id/bookings`: existing `X-Demo-Actor-Id` and nonempty opaque `Idempotency-Key` (maximum 128 characters), body `{platform: "web" | "mobile", journeyId: UUID}`. Unsupported attribution/payload fields are rejected. Fingerprint covers the normalized activity ID; platform/journey are observation context and can change on retry. Keys are scoped to actor and `book_activity`. Returns 201 for a new seat or 200 replay/recovery: `{booking, availability, replayed, telemetry: "ok" | "degraded"}`.
- `booking`: `{id, activityId, planId, userId, priceMinor, currency, confirmedAt}`; timestamp is absolute UTC. Its immutable price snapshot and plan membership are established only by a committed booking.
- `availability`: `{activityId, planId, capacity, confirmedCount, remainingSeats, version}`. Completed-key replay preserves the original response snapshot; use GET/details for current availability.
- `GET /api/activities/:id/booking`: selected existing actor required, returns `{booking: <record> | null, availability}` from one MVCC snapshot. Recovery works after capacity fills or activity starts/cancels; missing activity returns 404.
- Current domain rejections: 409 `SOLD_OUT`, `ACTIVITY_STARTED`, `ACTIVITY_UNAVAILABLE`, `IDEMPOTENCY_MISMATCH`; 400 `INVALID_REQUEST`; 401 `IDENTITY_REQUIRED`. These finalize the previously planned vocabulary above for this slice. Technical failures including bounded lock timeout return safe retryable 500 `INTERNAL_ERROR`; check confirmation/retry the same key. Rolled-back keys are not consumed. A failed initial confirmation lookup offers lookup retry and never creates a pending intent; same-request recovery is available only after a submitted or persisted intent. The web settles definitive rejections and clears their pending marker; only an uncertain response offers retry with the retained key.
- Each valid intent records `booking_attempted`. New committed business writes include exactly one `booking_succeeded`; each raw request records `booking_request_outcome` with `committed`, `replay`, `sold_out`, `invalid` or `technical_error`. Rejections also record `booking_sold_out` or `booking_failed` with stage/code/eligibility (`eligible`, `unknown`, `ineligible`, `sold_out`). Outcomes link request/key/operation/activity in context. Actor and activity-host synthetic/test markers propagate from resolved database rows, including invalid raw requests; request-body markers never determine classification. Invalid activity UUIDs record activityContext=invalid_id; valid UUIDs absent from storage record activityContext=not_found. Both contribute no activity/host flags and inherit only a resolved actor’s flags (false when no actor resolves). Telemetry storage failure preserves the original validation response. Invalid raw inputs, including malformed/oversized JSON, use the request UUID as correlation journey when no trusted journey exists; platform is marked unknown in context rather than treated as a mobile/web product observation.
- Attempt/failure/outcome writes are outside the business transaction. Telemetry exceptions log correlated diagnostics; `telemetry: degraded` warns after an otherwise successful booking. Durable success event failure rolls back the booking. Live delivery metrics are implemented below; booking/product metrics and production SLO attainment remain later work.
- `outbox_events` contains `availability_updated` with unique activity/version and booking reference. Payload `{eventId, ...availability}` is immutable domain context; dispatcher fields `attempts`, `dispatched_at`, `lease_until` and `retry_at` are writable. No Redis work runs during the booking transaction. Future invite claims extend this shared transaction after activity locking, preserving the existing booking before attribution/eligibility checks (PLANS.md §2.4); invitation validation and attribution are not implemented by this slice.


## Live availability slice (#7)

- WebSocket `/api/live` accepts the configured web Origin (or no Origin for native/test clients), JSON messages up to 4 KiB, and one activity subscription per connection. The Vite `/api` proxy supports WebSocket upgrades. Client messages: `{type: "subscribe", activityId, clientId: UUID, foreground: boolean}`, `{type: "foreground", foreground: boolean}`, and `{type: "ack", eventId, activityId, version}`. `clientId` identifies this view session and stays stable across reconnects; each server connection has a distinct ID. No contacts are transmitted.
- Server message `{type: "snapshot", eventId: UUID | null, activityId, version, capacity, confirmedCount, remainingSeats, activity}` includes the full activity detail and participants from a single PostgreSQL snapshot. `eventId=null` is an initial/reconciliation read; a booking delivery carries its durable outbox event ID. A later detail version can supersede the original event version. ACKs must refer to a delivery issued on that connection and a version between its booking version and the sent snapshot version.
- Register and buffer before reading the initial snapshot. Buffered deliveries then fetch committed detail. Reconnect and foreground entry refresh current details, and a one-second database reconciliation restores missed Redis messages on otherwise connected clients. Duplicate and older versions never replace newer rendered state; ACKs follow DOM commit. Connection interruption/delayed snapshots are visibly stale, and new booking submission stays disabled until live recovery. Existing confirmation and uncertain request recovery remain available.
- Redis channel `velio:group-bookings:v1:availability` carries the booking writer's outbox payload plus `bookingId` and `createdAt`. The dispatcher leases up to 20 pending rows in a short statement, publishes outside locks, and retries failed publication with capped exponential delay. Publication/marking failures can cause duplicates. An expired ten-second lease recovers a terminated dispatcher. Redis errors do not alter successful booking responses.
- `GET /api/metrics/live` reports distinct `commit_observed` and `pre_commit_proxy` groups. `includeTest` accepts only `true` or `false` (default false). `from`/`to` accept ISO timestamps with timezone; the default window is the preceding 24 hours, with a seven-day maximum. `window` states the bounds and persisted outbox `created_at` selection basis; ACK/deadline status is evaluated at query time. `reporting` states row/sample limits and completeness. At most 50,000 joined rows are processed; truncation explicitly marks partial counts and prevents an attainment claim. Use narrower windows for complete reports. Booking/client detail is limited to 100 each with omitted counts; summaries cover all processed rows.
- Latency quantiles are explicitly **ACK-only**: `ackOnlyPerBookingP95Ms` uses acknowledged per-booking maxima; `ackOnlyPooledP95Ms` pools acknowledged deliveries. `clients` provides actual `ackOnlyP95Ms`, expected/acknowledged/pending/miss counts and ACK sample counts per client; `worstClientAckOnlyP95Ms` reports the worst represented client quantile. Fully missed bookings/clients remain present with null latency and `latencyStatus=no_data`; partially acknowledged cohorts say `incomplete`. `ackOnlySamples`/`ackOnlyBookingSamples` expose successful latency denominators. These distributions never stand in for every-client attainment.
- `eventualAckCoverage` includes late ACKs; `onTimeCoverage` includes only ACKs within `targetMs=2000`. Any finalized miss or instrumentation gap makes `everyClientTargetMet=false`, even with pending deliveries. With no finalized miss, pending/no-data returns null. Missing/late ACKs persist; clients hiding or disconnecting after capture never retroactively leave the denominator.
- Exact local timing captures a process monotonic clock immediately after COMMIT returns and captures the ACK arrival on that same process. Remote publication and missed-event recovery use outbox creation time, explicitly a pre-commit proxy. The subscription’s initial snapshot version defines subsequent proxy deliveries; transaction-start timestamps never exclude a subscriber who joined before commit. Zero-subscriber bookings are observed but cannot establish delivery attainment. Historical instrumentation failure count is exposed for the current process; durable `instrumentationGaps` prevent a pass across all process endpoints and restarts. Failed observation writes retry the original cohort/clock. Process restarts cannot reconstruct exact local monotonic correlation; durable unacknowledged expectations remain misses. Multi-node exact timing correlation is a production follow-up. An ungracefully stopped gateway is conservatively treated as a possible instrumentation gap until its durable lifetime is reconciled; automatic crashed-process lifetime reconciliation is a production follow-up.

Expired event retransmissions are retired from memory after the two-second deadline; periodic current snapshots continue. Issued versions and original process clocks remain in durable delivery/observation records so a late ACK can still be verified and measured. Pending failed observations are capped at 512 and per-connection unacknowledged/buffered events at 256; exceeding a bound records an instrumentation gap or closes the slow connection, retaining durable missing-delivery evidence.


For an abrupt crash, an operator must verify that the gateway UUID logged at startup is terminated and record a trustworthy upper bound of its termination time. Using migration credentials, reconcile only that lifetime with parameterized SQL `UPDATE live_processes SET stopped_at=$2 WHERE process_id=$1 AND stopped_at IS NULL` (UUID and verified UTC bound). Keep observation/delivery rows: unknown coverage before that bound remains unknown; future bookings no longer require observations from a proven-dead gateway. Do not infer termination merely from missing ACKs or delete evidence to obtain a pass. Graceful shutdown first rejects new HTTP work and upgrades, drains accepted HTTP/booking work while observing commits, then persists one exclusive UTC observation cutoff (the gateway lifetime is `[started_at, stopped_at)`), reconciles events before it and drains already-started writes before closing PostgreSQL. Upgraded sockets are terminated after the observation drain; the HTTP listener close callback is awaited separately. Automatic fenced crash/lifetime detection is deferred; this manual step is an explicit assessment operational limitation.

Foreground eligibility is captured when a gateway observes the committed update: the socket must be connected, subscribed to that activity and client-reported foreground. Local origin captures immediately after COMMIT; remote/recovery captures at observation time and uses the labelled proxy. Initial versions filter only proxy deliveries. Foreground return resets the client watchdog grace period and requests fresh state. Later hide/disconnect interrupts rendering but does not remove captured expectations or erase historical misses.

Storage failure in measurement never prevents a current untagged availability snapshot. Failed observation writes retain the original cohort/clock; a bounded rotating ACK-write retry queue retains the original ACK arrival clock without closing a healthy socket. Failed writes and remain visible through diagnostics and durable observation gaps. Expired measurement records remain reportable and do not suppress current snapshot delivery. The gateway coalesces one pending reconciliation per subscriber, reuses one activity snapshot per tick, limits queued messages/updates to 256 and total connections to 1000. Indexed 100-row reconciliation pages advance a cursor and wrap, revisiting unresolved observations; large backlogs can delay measurement recovery while current snapshots continue.

Protocol UUIDs are normalized to lowercase; unknown fields, invalid object shapes/UUIDs/versions and nonboolean foreground flags close with 1008. Missing activities also close with 1008. Overloaded/slow clients close with 1013; denied Origin/path upgrades receive 403. Server `{type:"unavailable",message}` indicates a snapshot read failure, and clients retain stale details and reconnect. Expired records and unavailable telemetry alone do not produce this message. Local-origin Redis publications cannot replace the COMMIT clock with proxy timing. Both paths use the persisted outbox creation timestamp for proxy correlation.
