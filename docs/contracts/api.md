# Shared API contract, version 1

Current implementation and planned follow-up contracts for PLANS.md §2.3–2.6 and §4.1. Health/readiness, organic demo identities, host activity creation/inspection, and validated activity-view ingestion are implemented. Seat booking/recovery, the transactional outbox writer, live availability, and public invitations (creation, resolution, claims, invite-stamped signup and rendered opens) are also implemented. Recipient-bound vouches are implemented (see [Vouches](#vouches-issue-6)), as are the technical and product metrics endpoints (see [Queryable metrics](#queryable-technical-metrics-funnels-and-holdout-issue-10)). Sections labelled planned describe future boundaries. Changes to planned decisions must be recorded in PLANS.md §6.

## HTTP boundary

JSON under `/api`. Successful responses: `{ "data": <payload>, "requestId": "<server UUID>" }`. Errors: `{ "error": { "code": "NOT_FOUND", "message": "...", "retryable": false }, "requestId": "<server UUID>" }`. The server emits the same UUID in `X-Request-Id`; clients display safe messages and keep this reference for diagnosis. No stack traces or dependency credentials are returned. Dates are UTC ISO-8601 strings; activity display includes its IANA timezone. Monetary amounts are integer minor units plus currency.

- `GET /api/health`: 200, data `{ "status": "ok", "service": "velio-api" }`; process liveness only.
- `GET /api/ready`: checks PostgreSQL `SELECT 1` and Redis `PING` on each request; 200 data `{ "status": "ok", "dependencies": { "postgres": "ok", "redis": "ok" } }`. A dependency failure returns 503 with code `DEPENDENCIES_UNAVAILABLE`, retryable true. Readiness probes are bounded; liveness stays available during outages.
- Unknown paths: 404 `NOT_FOUND`. Invalid JSON: 400 `INVALID_JSON`. Oversized JSON: 413 `PAYLOAD_TOO_LARGE`. Unexpected errors: 500 `INTERNAL_ERROR`, retryable true.

Initial domain error vocabulary: `INVALID_REQUEST` (400), `IDENTITY_REQUIRED` (401), `RECIPIENT_MISMATCH`/`INVITE_NOT_ALLOWED` (403), `NOT_FOUND`/`INVALID_INVITE` (404), `SOLD_OUT`/`ALREADY_REDEEMED`/`IDEMPOTENCY_CONFLICT` (409), `INVITE_EXPIRED`/`ACTIVITY_STARTED` (410), and `TEMPORARILY_UNAVAILABLE` (503). Clients must inspect codes rather than parse messages. Domain tickets finalize endpoint payloads against the canonical plan; these names do not claim those routes exist.

## Booking writes and identity

Demo identity is explicitly selected and persisted; it is not production authentication. Booking writes carry the selected actor and `Idempotency-Key` (opaque UUID retained across uncertain outcomes). The server scopes keys by actor/operation and fingerprints payloads. Same key/same intent returns the committed result; changed payload returns `IDEMPOTENCY_MISMATCH`. A retry or own-booking lookup recovers confirmation before showing failure. Different keys still consume only one seat per user/activity. A transaction rollback leaves the intent retryable. Booking responses contain the committed booking, plan membership, price snapshot, and authoritative availability.

## Invitations and acquisition

`rail` is exactly `vouch` or `public`. Vouches are bound to one intended demo contact; public links allow distinct guests while capacity exists. Neither reserves seats. Codes are opaque server-issued values. Requests supply a code, never fabricated inviter, rail, root, or generation. Public previews exclude contacts. Expiry is the earlier of 24 hours after creation and activity start. Existing-booking recovery preserves its original attribution.

Signup generation is immutable product acquisition history: organic 0, new invite signup = inviter generation + 1, frozen parent/root and acquisition rail. Returning users retain signup history; later booking attribution is separate. Invites snapshot the inviter's signup ancestry.

## Events and guest journeys

Schema version `1`. Event envelope: `id` (UUID), `schemaVersion`, `name`, `occurredAt` (UTC), `source` (`server`/`client`), `platform` (`web`/`mobile`), optional `actorId`/persistent anonymous `journeyId`, relevant entity IDs, authoritative `rail`/`generation`, experiment version/assignment, outcome/reason, and synthetic marker. Optional fields are omitted when unknown, never invented. IDs deduplicate ingestion.

Persist a random guest journey ID before rendering an invite; retain it across opens, identity creation, and uncertain claims. `invite_opened` means a human rendered the preview, including full/expired states; link-preview GETs are not opens. Server success events persist atomically with their domain changes; attempt/failure telemetry survives rollback. No contact data in analytics. Event names and metric windows follow PLANS.md §4.1–4.2.

## Versioned availability

Snapshot: `{ "eventId": "<UUID>", "activityId": "...", "version": 1, "capacity": 2, "confirmedCount": 1, "remainingSeats": 1 }`. Versions increase with committed changes; counts come from PostgreSQL. Redis publication uses the durable outbox. Clients ignore duplicate/older versions, subscribe with snapshot recovery, reconcile periodically, and refresh on foreground/reconnect. ACK `{ "activityId": "...", "version": 1, "eventId": "..." }` only after visible application. Cached/offline capacity is labelled stale and cannot enable a claim. The implemented WebSocket endpoint and live delivery storage are described in the #7 slice below.

## CORS and readiness validation

The allowed WEB_ORIGIN is one validated HTTP(S) origin, normalized to its browser form. Preflight permits GET/POST/OPTIONS and Content-Type, Idempotency-Key, and X-Demo-Actor-Id (the planned demo identity header). Unapproved origins, methods, or headers receive 403 CORS_REQUEST_DENIED; unapproved origins are never reflected. Responses vary by Origin and preflight request method/headers. No cookie-credential CORS mode is enabled.

Both clients require an object envelope with a nonempty string request reference. A 200 readiness response must have status=ok and both dependencies ok; an error response must have a nonempty string code/message and boolean retryability. Unknown valid codes use safe connection guidance. Malformed/non-JSON responses show “The API returned an unexpected response. Please retry.” and never render unchecked reference fields. [Shared fixtures](readiness-fixtures.json) exercise error/malformed payload parity in both UI suites; request references are treated as opaque strings, while the API generates UUIDs.

## Host activity slice (#2)

- `POST /api/identities`: `{displayName, journeyId, platform, synthetic?, test?, inviteCode?, contact?}` (`inviteCode` from #5 and `contact` from #6; see those sections). `journeyId` is a UUID; platform is `web` or `mobile`; markers are booleans defaulting to false. Returns 201 `{id, displayName, generation: 0, acquisitionParentId: null, acquisitionRootId: id, synthetic, test}`. Signup ancestry and the server `identity_created` event persist atomically. Unknown fields (including invented referral ancestry) are rejected.
- `GET /api/identities`: all selectable demo identities, ordered by creation. This deliberately public demo directory exposes display names and ancestry IDs, never contact data. `GET /api/identities/:id` restores the same identity or returns `NOT_FOUND`.
- `POST /api/activities`: requires an existing `X-Demo-Actor-Id`. Body `{title, description, meetingLocation, startsAt, timezone, capacity, priceMinor, currency}`. Trimmed text limits are 120/2000/300 characters. `startsAt` is a valid absolute ISO calendar timestamp with seconds and `Z` or an explicit offset, normalized to UTC. `timezone` is an IANA zone (`UTC` also accepted). Input is resolved case-insensitively to a name supported by PostgreSQL and its display-timezone constraint, then checked by the backend Intl formatter before insertion. For example, `africa/lagos` is stored and returned as `Africa/Lagos`; unsupported zones return 400 `INVALID_REQUEST`, retryable false, with timezone guidance. Capacity is an integer in 1…2147483647; price is an integer in 0…2147483647 minor units; currency is an explicit uppercase three-letter code. This slice allows inspection of past activities too; booking eligibility is #3. Unknown fields are rejected. Returns 201 authoritative details.
- `GET /api/activities`: discovery list with `{id, hostId, title, description, meetingLocation, startsAt, timezone, status, capacity, confirmedCount, remainingSeats, priceMinor, currency, version, planId, assignment}`. `GET /api/activities/:id` adds `participants: [{id, displayName}]` from confirmed booking rows, excluding contacts, plus `invitePolicy` describing the selected actor’s current creation eligibility. New activities have scheduled status, version 1, zero confirmed count and capacity remaining. PostgreSQL creates one plan per activity; host creation creates no booking.
- `POST /api/events`: accepts schema-1 client `activity_viewed` and `experiment_exposed`. Exposure additionally requires `displayedInviteState` as defined below. Required `{id, schemaVersion: 1, name: 'activity_viewed' | 'experiment_exposed', source: 'client', occurredAt, platform, activityId}`; optional `{actorId, journeyId, planId, synthetic, test}`. At least selected actor or journey UUID is required. Any actor must match `X-Demo-Actor-Id` and exist. Activity must exist; supplied plan must belong to it. The server derives plan/generation and inherits selected-identity and activity-host markers, including anonymous seed views (a client cannot clear them). Invalid source/name, fabricated rail/generation, unknown fields, malformed timestamps/UUIDs and non-boolean markers are rejected. Returns 202 `{id, accepted: true}` for a new event, or `accepted: false` for an existing event ID, leaving the first record untouched. Only successful ingestion means durable receipt. Once details render, the web captures the event ID, actor, activity/plan, journey and occurrence time. App-owned delivery continues through ordinary in-app navigation and identity changes; every attempt is bounded to eight seconds. Failures remain visible in the app with a retry using the original ID, payload and actor header; server deduplication handles uncertain receipts.

Both boundaries validate inputs; PostgreSQL constraints additionally protect capacity, count bounds, timezone, price and currency. Runtime grants allow identity display-name updates, but no ancestry update/user deletion, signup-attribution update/delete, event update/delete, plan mutation or booking writes. Migration credentials alone run seeds. The read-only confirmed booking schema is established here; #3 adds the authoritative booking transaction, idempotency, attribution and outbox, plus its narrowly required runtime grants.

Web storage keys are versioned (`velio.actor.v1`, `velio.journey.v1`). Identities and activities load independently. Activity creation has a reversible pending list row; it never changes availability counts optimistically. A rejected request removes that row and preserves the form. A transport failure can occur after commit, so the UI asks users to refresh before retrying creation; activity-creation idempotency is not promised. Start input uses the device timezone, explicitly labelled, with both a selected display-zone preview and a UTC instant. Availability/participants are snapshots in #2; live updates belong to the later live ticket. Rendered-view delivery state is retained in memory for the current app session. Browser refresh/closure delivery is best effort and can lose pending or failed events; a persistent offline telemetry queue is outside this correction.

## Seat booking slice (#3)

- `POST /api/activities/:id/bookings`: existing `X-Demo-Actor-Id` and nonempty opaque `Idempotency-Key` (maximum 128 characters), body `{platform: "web" | "mobile", journeyId: UUID}`. Unsupported attribution/payload fields are rejected. Fingerprint covers the normalized activity ID; platform/journey are observation context and can change on retry. Keys are scoped to actor and `book_activity`. Returns 201 for a new seat or 200 replay/recovery: `{booking, availability, replayed, telemetry: "ok" | "degraded"}`.
- `booking`: `{id, activityId, planId, userId, priceMinor, currency, confirmedAt}`; timestamp is absolute UTC. Its immutable price snapshot and plan membership are established only by a committed booking.
- `availability`: `{activityId, planId, capacity, confirmedCount, remainingSeats, version}`. Completed-key replay preserves the original response snapshot; use GET/details for current availability.
- `GET /api/activities/:id/booking`: selected existing actor required, returns `{booking: <record> | null, availability}` from one MVCC snapshot. Recovery works after capacity fills or activity starts/cancels; missing activity returns 404.
- Current domain rejections: 409 `SOLD_OUT`, `ACTIVITY_STARTED`, `ACTIVITY_UNAVAILABLE`, `IDEMPOTENCY_MISMATCH`; 400 `INVALID_REQUEST`; 401 `IDENTITY_REQUIRED`. These finalize the previously planned vocabulary above for this slice. Technical failures including bounded lock timeout return safe retryable 500 `INTERNAL_ERROR`; check confirmation/retry the same key. Rolled-back keys are not consumed. A failed initial confirmation lookup offers lookup retry and never creates a pending intent; same-request recovery is available only after a submitted or persisted intent. The web settles definitive rejections and clears their pending marker; only an uncertain response offers retry with the retained key.
- Each valid intent records `booking_attempted`. New committed business writes include exactly one `booking_succeeded`; each raw request records `booking_request_outcome` with `committed`, `replay`, `sold_out`, `invalid` or `technical_error`. Rejections also record `booking_sold_out` or `booking_failed` with stage/code/eligibility (`eligible`, `unknown`, `ineligible`, `sold_out`). Outcomes link request/key/operation/activity in context. Actor and activity-host synthetic/test markers propagate from resolved database rows, including invalid raw requests; request-body markers never determine classification. Invalid activity UUIDs record activityContext=invalid_id; valid UUIDs absent from storage record activityContext=not_found. Both contribute no activity/host flags and inherit only a resolved actor’s flags (false when no actor resolves). Telemetry storage failure preserves the original validation response. Invalid raw inputs, including malformed/oversized JSON, use the request UUID as correlation journey when no trusted journey exists. When the body names a valid platform it is recorded with `platformKnown: true`; otherwise the column records `web` and `platformKnown: false` marks it unknown rather than a product observation. Since #5 a `completed` activity is rejected with `ACTIVITY_STARTED`, like a past start; only `cancelled` returns `ACTIVITY_UNAVAILABLE`.
- Attempt/failure/outcome writes are outside the business transaction. Telemetry exceptions log correlated diagnostics; `telemetry: degraded` warns after an otherwise successful booking. Durable success event failure rolls back the booking. Live delivery metrics are implemented below; booking/product metrics and production SLO attainment remain later work.
- `outbox_events` contains `availability_updated` with unique activity/version and booking reference. Payload `{eventId, ...availability}` is immutable domain context; dispatcher fields `attempts`, `dispatched_at`, `lease_until` and `retry_at` are writable. No Redis work runs during the booking transaction. Future invite claims extend this shared transaction after activity locking, preserving the existing booking before attribution/eligibility checks (PLANS.md §2.4); invitation validation and attribution are not implemented by this slice.


## Live availability slice (#7)

- WebSocket `/api/live` accepts the configured web Origin (or no Origin for native/test clients), JSON messages up to 4 KiB, and one activity subscription per connection. The Vite `/api` proxy supports WebSocket upgrades. Client messages: `{type: "subscribe", activityId, clientId: UUID, foreground: boolean}`, `{type: "foreground", foreground: boolean}`, and `{type: "ack", eventId, activityId, version}`. `clientId` identifies this view session and stays stable across reconnects; each server connection has a distinct ID. No contacts are transmitted.
- Server message `{type: "snapshot", eventId: UUID | null, activityId, version, capacity, confirmedCount, remainingSeats, activity}` includes the full activity detail and participants from a single PostgreSQL snapshot. `eventId=null` is an initial/reconciliation read; a booking delivery carries its durable outbox event ID. A later detail version can supersede the original event version. ACKs must refer to a delivery issued on that connection and a version between its booking version and the sent snapshot version.
- Register and buffer before reading the initial snapshot. Buffered deliveries then fetch committed detail. Reconnect and foreground entry refresh current details, and a one-second database reconciliation restores missed Redis messages on otherwise connected clients. Duplicate and older versions never replace newer rendered state; ACKs follow DOM commit. Connection interruption/delayed snapshots are visibly stale, and new booking submission stays disabled until live recovery. Existing confirmation and uncertain request recovery remain available.
- Redis channel `velio:group-bookings:v1:availability` carries the booking writer's outbox payload plus `bookingId` and `createdAt`. The dispatcher leases up to 20 pending rows in a short statement, publishes outside locks, and retries failed publication with capped exponential delay. Publication/marking failures can cause duplicates. An expired ten-second lease recovers a terminated dispatcher. Redis errors do not alter successful booking responses.
- `GET /api/metrics/live` reports distinct `commit_observed` and `pre_commit_proxy` groups. `includeTest` accepts only `true` or `false` (default false). `from`/`to` accept ISO timestamps with timezone; the default window is the preceding 24 hours, with a seven-day maximum. `window` states the bounds and persisted outbox `created_at` selection basis; ACK/deadline status is evaluated at query time. `reporting` states row/sample limits and completeness. At most 50,000 joined rows are processed; truncation explicitly marks partial counts and prevents an attainment claim. Use narrower windows for complete reports. Booking/client detail is limited to 100 each with omitted counts; summaries cover all processed rows.
- Latency quantiles are explicitly **ACK-only**: `ackOnlyPerBookingP95Ms` uses acknowledged per-booking maxima; `ackOnlyPooledP95Ms` pools acknowledged deliveries. `clients` provides actual `ackOnlyP95Ms`, expected/acknowledged/pending/miss counts and ACK sample counts per client; `worstClientAckOnlyP95Ms` reports the worst represented client quantile. Fully missed bookings/clients remain present with null latency and `latencyStatus=no_data`; partially acknowledged cohorts say `incomplete`. `ackOnlySamples`/`ackOnlyBookingSamples` expose successful latency denominators. These distributions never stand in for every-client attainment.
- `eventualAckCoverage` includes late ACKs; `onTimeCoverage` includes only ACKs within `targetMs=2000`. Any finalized miss or instrumentation gap makes `everyClientTargetMet=false`, even with pending deliveries. With no finalized miss, pending/no-data returns null. Missing/late ACKs persist; clients hiding or disconnecting after capture never retroactively leave the denominator.
- Exact local timing captures a process monotonic clock immediately after COMMIT returns and captures the ACK arrival on that same process. Remote publication and missed-event recovery use outbox creation time, explicitly a pre-commit proxy. The subscription’s initial snapshot version defines subsequent proxy deliveries; transaction-start timestamps never exclude a subscriber who joined before commit. Zero-subscriber bookings are observed but cannot establish delivery attainment. Historical instrumentation failure count is exposed for the current process; durable `instrumentationGaps` prevent a pass across all process endpoints and restarts. Failed observation writes retry the original cohort/clock. Process restarts cannot reconstruct exact local monotonic correlation; durable unacknowledged expectations remain misses. Multi-node exact timing correlation is a production follow-up. An ungracefully stopped gateway is conservatively treated as a possible instrumentation gap until its durable lifetime is reconciled; automatic crashed-process lifetime reconciliation is a production follow-up.

Expired event retransmissions are retired from memory after the two-second deadline; periodic current snapshots continue. Issued versions and original process clocks remain in durable delivery/observation records so a late ACK can still be verified and measured. Pending failed observations are capped at 512 and per-connection unacknowledged/buffered events at 256; exceeding a bound records an instrumentation gap or closes the slow connection, retaining durable missing-delivery evidence.


For an abrupt crash, an operator must verify that the gateway UUID logged at startup is terminated and record a trustworthy upper bound of its termination time. Using migration credentials, reconcile only that lifetime with parameterized SQL `UPDATE live_processes SET stopped_at=$2 WHERE process_id=$1 AND stopped_at IS NULL` (UUID and verified UTC bound). Keep observation/delivery rows: unknown coverage before that bound remains unknown; future bookings no longer require observations from a proven-dead gateway. Do not infer termination merely from missing ACKs or delete evidence to obtain a pass. Graceful shutdown first rejects new HTTP work and upgrades, drains accepted HTTP/booking work while observing commits, then persists one exclusive UTC observation cutoff (the gateway lifetime is `[started_at, stopped_at)`), reconciles events before it and drains already-started writes before closing PostgreSQL. Upgraded sockets are terminated after the observation drain; the HTTP listener close callback is awaited separately. Automatic fenced crash/lifetime detection is deferred; this manual step is an explicit assessment operational limitation.

Foreground eligibility is captured when a gateway observes the committed update: the socket must be connected, subscribed to that activity and client-reported foreground. Local origin captures immediately after COMMIT; remote/recovery captures at observation time and uses the labelled proxy. Initial versions filter only proxy deliveries. Foreground return resets the client watchdog grace period and requests fresh state. Later hide/disconnect interrupts rendering but does not remove captured expectations or erase historical misses.

Storage failure in measurement never prevents a current untagged availability snapshot. Failed observation writes retain the original cohort/clock; a bounded rotating ACK-write retry queue retains the original ACK arrival clock without closing a healthy socket. Failed writes and remain visible through diagnostics and durable observation gaps. Expired measurement records remain reportable and do not suppress current snapshot delivery. The gateway coalesces one pending reconciliation per subscriber, reuses one activity snapshot per tick, limits queued messages/updates to 256 and total connections to 1000. Indexed 100-row reconciliation pages advance a cursor and wrap, revisiting unresolved observations; large backlogs can delay measurement recovery while current snapshots continue.

Protocol UUIDs are normalized to lowercase; unknown fields, invalid object shapes/UUIDs/versions and nonboolean foreground flags close with 1008. Missing activities also close with 1008. Overloaded/slow clients close with 1013; denied Origin/path upgrades receive 403. Server `{type:"unavailable",message}` indicates a snapshot read failure, and clients retain stale details and reconnect. Expired records and unavailable telemetry alone do not produce this message. Local-origin Redis publications cannot replace the COMMIT clock with proxy timing. Both paths use the persisted outbox creation timestamp for proxy correlation.

### Invitation experiment (issue #4)

Activity list/details include `assignment`: `{ experiment: "group_invites_v1", version,
variant: "treatment" | "control", treatmentPercent, assignedAt }`. Details and creation
responses include `invitePolicy`: `{ assignment, creationEnabled, allowed, reason }`.
The optional actor header selects the policy's actor. Unknown actors receive 401
`IDENTITY_REQUIRED`, malformed actor UUIDs receive 400 `INVALID_REQUEST`, and known
ineligible actors receive the policy result. Missing actors may browse and book after
selecting an identity. Creation responses evaluate the host's policy.

Every committed activity must have one assignment. Migration 005 backfills activities
that predate assignment storage. Corrective migration 006 validates that invariant
and adds a deferred reverse foreign key, so later writers must explicitly supply an
assignment in the activity transaction. It never chooses implicit trigger defaults.
An incomplete legacy database fails migration 006 visibly and requires an explicit
cohort decision/repair. Independent checks enforce hash/bucket and bucket/variant.
Runtime credentials may insert/read assignments but cannot rewrite/delete them.

Reads use left joins: administrative damage does not hide activities. A missing
assignment is represented by `assignment: null` with an `assignment_unavailable`
policy, not a misleading activity 404. Ordinary booking remains independent. Web
validates assignment and policy fields; missing/malformed invitation data renders
unavailable while activity details and booking stay usable.

`GET /api/activities/:id/invite-eligibility` returns the same policy result. Reasons
are `allowed`, `creation_disabled`, `control`, `host_or_booker_required`, and
`assignment_unavailable`. Missing assignments fail closed. Otherwise creation requires
the global switch, treatment assignment and a host/confirmed-booker actor. The app
requires explicit invite configuration and binds `createInvitePolicy` once; future
creation handlers must call its `requireCreation` method at the write boundary.
The read endpoint is presentation, not authorization for a later write. Intended
future resolution/claim handling remains independent of the creation-only switch.
Those routes are not implemented by this ticket.

`POST /api/events` accepts only strict string names `activity_viewed` and
`experiment_exposed`. Exposure additionally requires `displayedInviteState`:
`{ enabled: boolean, creationEnabled: boolean, reason: <policy reason> }`. This is
client-reported display context, stored under that name separately from authoritative
`context.assignment` derived from PostgreSQL. It describes what actually rendered,
not what the current switch would allow when a delayed retry reaches the server.
Invalid/missing display fields and non-string names (including arrays) are rejected.
Activity views cannot supply exposure display state. Clients cannot supply assignment.
Activity-view and resolved booking events carry authoritative assignment context;
booking requests with invalid activity IDs, nonexistent activities, or damaged missing
assignments carry null instead of a fabricated cohort. Malformed booking requests
that resolve an existing assigned activity retain its authoritative assignment.

Exposure is captured after the invitation section renders, including disabled and
unavailable states. No event is emitted merely by listing, creating, or loading an
activity. In one app session, unchanged state for the same activity and actor (or
anonymous journey) is suppressed across booking/details refreshes and navigation.
A changed displayed state gets a new ID; delivery retries keep the original ID,
payload and actor header. Identity changes have independent observations. Browser
reload starts a new session; storage/closure delivery remains best effort.

Ingestion deduplicates exact event IDs. For analytical reach, use the first exposure
per activity/experiment-version and resolved actor, falling back to journey when no
actor is resolved; unresolved cross-device identities remain a limitation. Display
state breakdowns may keep the first per distinct reported `(enabled, creationEnabled,
reason)` within that observation unit, rather than count refreshes as new people.
State transitions remain inspectable. Pre-correction events without display context
are unknown display state, never inferred from today's switch. All assigned activities,
including holdout and those without exposure, remain the experiment denominator;
exposure filtering must not condition the activity-level outcome comparison.

Shared WebSocket snapshots carry actor-independent availability and participants. Web retains actor-specific invitation policy from the HTTP detail response; delayed HTTP policy refresh cannot roll back newer live membership. During an actor refresh, ACKs wait until that actor's activity view is rendered.

## Public invitations (issue #5)

Shared by web, Flutter (#8) and vouches (#6). Codes are 12 characters of Crockford base32 without `I`, `L`, `O` or `U` (`^[0-9A-HJKMNP-TV-Z]{12}$`), generated server-side from random bytes; they encode nothing about the activity. Every route accepts lowercase and grouped input (`abcd-2345 efgh`) and normalizes it. Clients display codes in groups of four. Web link: `<web origin>/invite/<CODE>`. Installed-app link: `velio://invite/<CODE>?journey=<journey UUID>`; the app should adopt that journey when it has none, so a web open and an app claim share one guest journey. Deferred install linking is not assumed, so code entry remains the dependable fallback (and that cross-device path stays uncorrelated).

- `POST /api/activities/:id/invites`: existing `X-Demo-Actor-Id`; body `{rail: "public" | "vouch", recipientContact?, platform: "web" | "mobile", journeyId?: UUID}`; `recipientContact` is required for `vouch` and rejected for `public` (see [Vouches](#vouches-issue-6)). Other rails and unknown fields (including inviter/generation) return 400. Creation calls the bound `requireCreation` policy: treatment assignment, creation switch on, and a host or confirmed booker; otherwise 403 `INVITE_CREATION_UNAVAILABLE`. Cancelled activities return 409 `ACTIVITY_UNAVAILABLE`; started or completed activities return 409 `ACTIVITY_STARTED`; full activities return 409 `SOLD_OUT`. Eligibility and the insert run in one statement, so an activity starting or filling mid-request returns these codes rather than a technical error. Returns 201 `{id, code, rail, inviterRole: "host" | "booker", activityId, planId, createdAt, expiresAt, availability: {capacity, confirmedCount, remainingSeats, version}}`, plus `recipientContact` for a vouch. `expiresAt` is the earlier of `createdAt + 24h` and the activity start. Each call issues a new code; nothing is reserved. `invite_created` commits in the same statement as the invite.
- `GET /api/invites/:code`: public preview, no identity required, never records an event (link unfurlers and prefetches are not opens). Returns `{code, rail, trust (equal to rail: "public" or "vouch"), state, createdAt, expiresAt, inviter: {displayName, role}, activity: {id, planId, title, description, meetingLocation, startsAt, timezone, status, capacity, confirmedCount, remainingSeats, priceMinor, currency, version}}`. No inviter ID or contact data is exposed. `state` precedence, evaluated at one observation time: `cancelled` (status) → `started` (completed status, or start passed) → `expired` → `full` → `valid`. Signup and claims use the same classification. Unknown or malformed codes return 404 `INVALID_INVITE`.
- `POST /api/invites/:code/claims`: existing actor, `Idempotency-Key`, body `{platform, journeyId}`; any other field is rejected. Validation order matches direct booking: identity (401 `IDENTITY_REQUIRED`, worded for claiming), request shape, then the code (404 `INVALID_INVITE`). Keys are scoped to actor and `claim_invite` and fingerprint the activity and invite. Inside the shared booking transaction, after the activity row lock: (1) an existing booking for the actor is returned with 200 `replayed: true` and its original `redemption` (or null for a direct booking), even if the link is now full, expired or the actor's own; (2) cancelled → 409 `ACTIVITY_UNAVAILABLE`, started or completed → 409 `ACTIVITY_STARTED`; (3) inviter claiming their own link → 403 `SELF_INVITE`; (4) vouch only: a claimant whose identity contact is not the intended one → 403 `RECIPIENT_MISMATCH`; (5) expired → 410 `INVITE_EXPIRED`; (6) vouch only, defensive: already redeemed → 409 `ALREADY_REDEEMED`; (7) no seat → 409 `SOLD_OUT`. Success returns 201 `{booking, availability, replayed: false, redemption: {id, inviteId, bookingId, rail, inviteeGeneration, createdAt}, telemetry}`. Booking, count/version, redemption, `booking_succeeded`, `spot_claimed`, idempotency result and outbox commit together; failure rolls all of them back. Issued links keep working after the creation switch is turned off or rollout changes.
- `POST /api/identities` accepts optional `inviteCode`. A live issued code (preview state `valid` or `full`) stamps the new user with the invite's snapshot: generation = inviter generation + 1, parent = inviter, root = inviter's root, rail and invite. Unusable codes return the same errors as a claim: unknown 404 `INVALID_INVITE`, cancelled 409 `ACTIVITY_UNAVAILABLE`, started or completed 409 `ACTIVITY_STARTED`, a vouch without the matching `contact` 403 `RECIPIENT_MISMATCH`, expired 410 `INVITE_EXPIRED`. The client may retry without the code as an organic signup. Invite signups' `identity_created` carries the invite's activity, plan and persisted assignment. Identity responses add `acquisitionRail` (`null` for organic). Signup is not activation: activation requires a committed claim. Invited identities inherit the inviter's synthetic/test markers.
- `POST /api/events` accepts client `invite_opened`: `{id, schemaVersion: 1, name: "invite_opened", source: "client", occurredAt, platform, journeyId (required), inviteCode, displayedState: "valid" | "full" | "expired" | "started" | "cancelled", actorId?, synthetic?, test?}`. Send it only after the preview is visible to a person, including full/expired states. The server derives invite, activity, plan, rail, inviter role/generation, assignment, the authoritative `stateAtReceipt`, viewer `generation` (actor only) and `recovery` (true when the actor already holds a booking for that activity). Rail, generation, inviter and assignment fields from clients are rejected. Event IDs deduplicate retries (`accepted: false`).

Claim telemetry: each valid claim records `booking_attempted` and `invite_claim_attempted` before the transaction; `booking_failed`/`booking_sold_out` and `booking_request_outcome` (`operation: "claim_invite"`) survive rollback; recoveries record outcome `replay` and no new `spot_claimed`. Claim events from valid requests carry `invite_id`, platform, journey, `rail`, the actor's signup `generation` and the persisted assignment. Invalid claim requests record only `booking_request_outcome` with `operation: "claim_invite"`, invite/activity context when the code resolves, and the body's platform when valid.

Markers: every invite event (`invite_created`, `invite_opened`, `identity_created`, claim attempts, successes and outcomes) is synthetic/test when the actor or viewer, the activity host or the inviter is; client-supplied markers can add but never clear them.

History: `invites`, `invite_redemptions` and `signup_attribution` are insert-only for the runtime role, and append-only triggers refuse ordinary UPDATE/DELETE from any role. Users' ancestry columns are immutable; display names remain editable. Composite foreign keys reject an invited user, signup attribution or redemption that does not match the stored invite snapshot. Corrections append to `attribution_corrections` (`subject`, `subject_id`, `reason`, `correction`) using migration credentials; runtime can read them only. This protects history from application mutation, not from an administrator replacing the database.

Finalized error codes for this slice: 404 `INVALID_INVITE`, 403 `INVITE_CREATION_UNAVAILABLE` and `SELF_INVITE`, 410 `INVITE_EXPIRED`, plus the booking codes above. Vouches (#6) add 403 `RECIPIENT_MISMATCH`, 409 `CONTACT_IN_USE` and the defensive 409 `ALREADY_REDEEMED`.

## Vouches (issue #6)

A vouch is the `vouch` rail of the same invitation contract above: same code format, links, preview states, expiry, creation policy, claim transaction and events. Differences are additive:

- `POST /api/identities` accepts optional `contact`: an email address (lowercased) or phone number (spaces, dashes, dots and parentheses removed; 7–15 digits, optional leading `+`). Normalization makes no other inference: phone numbers are matched exactly as entered (no country code is added or removed), so the inviter and guest must use the same format. Email parts may contain international letters but not `@`, controls (including NUL and U+0085), spaces, Unicode space separators, zero-width or bidi formatting characters, or the byte-order mark; any such input returns 400 `INVALID_REQUEST`. The API and the database check (`is_demo_contact`, migration 011) exclude the same code points, so no accepted contact can fail in PostgreSQL. It is a demo contact, unverified, set once at signup and unique when present; a duplicate returns 409 `CONTACT_IN_USE`. Identity responses and listings never include it.
- `POST /api/activities/:id/invites` accepts `{rail: "vouch", recipientContact, platform, journeyId?}`. `recipientContact` is required for `vouch` and rejected for `public` (400 `INVALID_REQUEST`, also for an invalid contact). Vouching for the inviter's own contact returns 403 `SELF_INVITE`. Policy, capacity and activity-state errors are identical to public links. The 201 response adds `recipientContact` (normalized), returned only to the inviter who entered it.
- `GET /api/invites/:code` returns `rail: "vouch"` and `trust: "vouch"`. It never includes or hints at the intended contact, and has no separate "used" state: only the recipient could act on that, and their claim recovers their booking.
- Claims add one check, after the self-invite check and before expiry, judged inside the booking transaction after the activity row lock: a claimant whose identity contact is absent or different gets 403 `RECIPIENT_MISMATCH` (the message never names the contact). A vouch has one logical successful redemption; existing-booking recovery still comes first, so the recipient reopens the same confirmation by key or by membership even when the activity is full or the vouch is used. Wrong-recipient, sold-out, expired and rolled-back claims consume neither a seat nor the vouch. `409 ALREADY_REDEEMED` is a defensive code that unique contacts make unreachable. Recovery precedes the recipient check (§2.3), so a non-recipient who already holds a booking for the activity gets that booking back (200, `replayed`, with its own original `redemption` or null); nothing is consumed and the response is not a vouch redemption, so clients should present it as their existing booking.
- Signup with a vouch `inviteCode` must supply the matching `contact`; otherwise 403 `RECIPIENT_MISMATCH`. A matching signup is acquired with rail `vouch`.
- Events: `invite_created`, `invite_opened`, `identity_created` and claim events carry server-derived `rail: "vouch"` and generation exactly as for public links, and never the contact. Wrong-recipient claims record `booking_failed` with code `RECIPIENT_MISMATCH`, stage `invite`.
- Demo limitation (contact enumeration): because contacts are unique and signup is unauthenticated, anyone can learn whether a contact belongs to some demo identity (`POST /api/identities` with that `contact` returns 409 `CONTACT_IN_USE`); no vouch code is needed. Someone holding a vouch code can additionally test guesses against it (403 for a wrong contact). Contacts are never returned, but their existence is not secret in this demo. Matching simulates a trusted introduction and is not access control: whoever first registers the intended contact can claim. Production needs verified contacts, rate limits and responses that do not reveal registration (PLANS.md §6).

## Queryable technical metrics, funnels and holdout (issue #10)

Both endpoints take the same parameters as `/api/metrics/live`: `includeTest` (`true`/`false`, default `false`) and `from`/`to` ISO timestamps with timezone (default preceding 24 hours, at most seven days). Invalid parameters return 400 `INVALID_REQUEST`. With `includeTest=false`, any event, user, host or activity marked synthetic or test is excluded from every count; the demo seeds are all synthetic, so the default view of a seeded database is empty by design (`no_data`, never a fabricated 0%).

- `GET /api/metrics/summary` reports technical health for the window:
  - `integrity` reads `booking_reconciliation` current state: activities checked, oversold activities, counter mismatches, target 0 and the violating rows (`capacity`, `bookingCount`, `confirmedCount`).
  - `bookings.rawOutcomes` counts every `booking_request_outcome` by `committed`, `replay`, `soldOut`, `invalid`, `technicalError` and total; `bookings.attempts` counts `booking_attempted` events. Raw request counts never collapse retries.
  - `bookings.reliability` classifies distinct logical intents, keyed by (actor, operation, activity, invite) from `booking_request_outcome` context within the window; a request whose identity never resolved is its own intent, so its failure stays counted. An intent succeeds when any request committed or replayed a committed result; an eligible technical failure had capacity confirmed (`eligibility: eligible`) and never succeeded; an unknown failure failed before capacity could be established. Sold-out and invalid domain rejections are excluded from the rates but stay in raw counts. `retriedIntents` counts intents with more than one request and `technicalErrorRate` is technical errors per raw request. `eligibleRate` is S/(S+F), `unknownInclusiveRate` the conservative S/(S+F+U); `resolvedIntents` is S+F. `status` is `no_data`, `insufficient_sample` (below the 1,000-resolved-intent trigger) or `observed`. Local `observed` numbers are not production SLO attainment.
  - `live` summarizes delivery in the same window (expected/acknowledged/pending/misses per timing group, ACK-only per-booking-max p95 using the live report's nearest-rank definition) and points at `/api/metrics/live` for the complete per-client latency, coverage and instrumentation-gap report that endpoint owns.

- `GET /api/metrics/product` reports the three product queries and the holdout comparison:
  - `bookersInvite`: each user's first confirmed booking in the window qualifies; the user is invited when an invite exists for that activity within 24h of that booking. `mature` covers bookings whose 24h window closed inside the reporting window; `notYetMature` is reported separately, never mixed into the rate. `invitedByRail` segments the numerator and `bySignupGeneration` segments mature bookers by the booker's signup generation; `hostCreatorsWithoutBooking` counts host-role inviters with no booking ever as the separate creator segment. Target 0.30 and the >=200 mature-journey trigger are shown with `status` (`no_data`/`insufficient_sample`/`observed`) and a Wilson 95% interval on the mature rate.
  - `openToClaim`: units are deduplicated `(invite, guest journey)` first opens (view `metric_invite_open_units`, migration 012). A unit converts when its attributed `spot_claimed` on the same invite and journey occurs within the earlier of 24h and the activity start (inclusive bounds). Recovery reopens by existing bookers are not acquisition: they are counted in `reasons.recoveryOpens` and excluded from every rate. `headline` keeps all other human opens including full/expired previews; `eligible` keeps only `valid` previews. `reasons.byDisplayedState` diagnoses the excluded mass. Segments: `byRail`, `byPlatform`, `byInviterGeneration`, `byAvailabilityAtOpen`, `byViewer` (`new` = no identity at first open, `returning` = an existing identity). Target 0.25, >=200 mature-journey trigger, Wilson interval, `status`.
  - `kFactor`: the cohort is every user existing at window start who had already hosted or booked (including non-inviters), frozen at `cohort.asOf`. Numerators are distinct new users in the window whose frozen acquisition parent is a cohort member, split by frozen acquisition rail; `activatedK` requires an invitation claim (redemption) inside the window. `window.days` is reported; windows shorter than the planned seven days return `status: "partial_window"`. Both rails share the cohort denominator. `newUsersByGeneration` shows all new users by generation; descendants of window-acquired users (and acquisitions by users who only became hosts/bookers inside the window) belong to later cohorts and stay out of direct K. `target` is null: no numerical K goal is invented.
  - `holdout`: per experiment version, every activity assigned in the window (assignment, not exposure, is the denominator) with bookings confirmed before the window ends as participants (so a report stays fixed) and a provisional formed plan at >=2 participants. Treatment minus control is reported for mean participants per activity (with a Welch-style 95% interval when each arm has >=2 activities) and formed-plan rate. `attendance` is `unmeasured`, `observationalOnly` is true; no causal claim is made and small-sample intervals are wide by construction.

Empty cohorts return `no_data`/null rates rather than 0%. The labelled seed `backend/seeds/metrics.sql` (applied by `npm run seed`, all synthetic) reproduces reliability outcomes, repeated/full/recovery opens, the 24h and activity-start deadline boundaries, host invites, returning users, lineage generations and both holdout arms in the historical window 2026-10-01..2026-10-08; query with `includeTest=true`. `backend/test/metrics.test.ts` verifies the same definitions against hand-calculated expectations on an isolated database, including observation-window boundaries and overlapping journeys.
