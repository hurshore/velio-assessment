# Public invitations — issue #5

Scope: PLANS.md §§1.2, 1.4, 2.3, 2.4, 2.6, 2.7, 3.1–3.3 and 4.1. Node 24.21.0 and PostgreSQL 17.6. Real HTTP requests run with runtime credentials against a disposable database per suite (`backend/test/invites.test.ts`). The web uses jsdom component tests with a stubbed `fetch` (`web/src/PublicShare.test.tsx`, `web/src/GuestInvite.test.tsx`).

## Verified behaviour

- **Creation.** Host and confirmed-booker creation works in treatment. Outsiders, control activities and a disabled creation switch get 403. Unknown actors get 401. Forged `inviterId` and the unsupported `vouch` rail get 400. Full, started and cancelled activities get 409. Codes are 12-character Crockford base32, and each request issues a new code. Expiry is exactly `createdAt + 24h`, or the activity start when that is earlier. Creating a link leaves availability unchanged. `invite_created` stores platform, journey, rail, inviter role/generation and the persisted assignment.
- **Preview.** Resolution returns `valid`, `full`, `expired`, `started` and `cancelled` states, accepts lowercase and grouped codes, and returns 404 `INVALID_INVITE` for unknown or malformed codes. It never exposes the inviter's ID and records no `invite_opened` event.
- **Claims.** Two distinct guests claim one link until capacity is reached; the third gets `SOLD_OUT`. A replay with the same key, or a new key from the same member, returns the original booking and redemption even when the activity is full. A self-claim (403), an invalid code (404) or an expired code (410) consumes no seat or redemption. A guest with an earlier direct booking gets that booking back with `redemption: null`, and no edge is written.
- **Races.** 30 coordinated requests (15 direct bookings and 15 claims) target 3 seats while the activity row is externally locked. At least 10 lock waiters are confirmed. Result: exactly 3 commits, 27 `SOLD_OUT`, reconciliation clean, and redemption and `spot_claimed` counts equal to the winning claims. Sixteen concurrent duplicate claims from one guest (8 sharing a key, 8 with fresh keys) commit one booking and one redemption. A key reused for a different invite returns `IDEMPOTENCY_MISMATCH`.
- **Rollback and expiry boundary.** A failure injected on redemption insert returns retryable 500 and rolls back booking, count/version, success events and the key. `booking_attempted`, `invite_claim_attempted` and `booking_failed` survive. The same key then succeeds. A link moved to expire 700 ms later accepts a claim before expiry and returns `INVITE_EXPIRED` (preview `expired`) after it.
- **Kill switch.** After restarting with creation disabled and a different rollout, a previously issued link still previews as valid, stamps a signup and claims a seat. New creation returns 403.
- **Acquisition chain.** Organic generation 0 → invited 1 → invited 2: parent, root and rail are frozen and `signup_attribution` matches. Each invite snapshots its inviter's history. A returning organic user redeems with `inviteeGeneration` 0 and keeps an unchanged signup history. A signup without a claim has no `spot_claimed`. Unknown, expired and cancelled-activity signup codes return 404, 410 and 409 respectively; forged generation and parent fields return 400. Invite signups' `identity_created` carries activity, plan and assignment; organic signups carry none.
- **Immutability.** Runtime UPDATE/DELETE on invites, redemptions, signup attribution and users' ancestry, and runtime INSERT of corrections, all fail with permission denied. Migration-role UPDATE/DELETE of history is refused by append-only triggers, while display-name edits still work. A correction appends and is readable by runtime. Runtime inserts with forged ancestry, invite snapshot or redemption inviter fail on foreign keys.
- **Journey correlation.** One journey ID connects `invite_opened` → `identity_created` → `invite_claim_attempted` → `spot_claimed`, each with platform `mobile` and rail `public`, and the claim events carry generation and assignment. Event-ID replay is deduplicated. Forged rail, generation, inviter or display state, and a missing journey, are rejected. A reopen by a confirmed guest records `recovery: true`, and a claim replay records outcome `replay` with no second `spot_claimed`. A different journey's open of the full link is recorded.
- **Seeds.** `seeds/invites.sql` replays without changes. It contains Amara (0) → Kemi (1) → Zainab (2), returning Tunde (0), three redemption edges, an attempt event before every `spot_claimed`, clean reconciliation, synthetic `attribution-chain` events, and an expired-state open.
- **Web.** The share panel explains public trust, remaining seats, expiry and that no seat is reserved before creation. It then shows the link, the grouped code, Copy (clipboard) and Share (share sheet; cancelling is silent). Rejections are shown and the panel stays usable; a full activity disables creation. The guest preview at `/invite/<code>` shows inviter, activity, zoned time, price and availability without identity setup, plus the code and `velio://invite/<code>?journey=<journey>`. It sends one `invite_opened` under StrictMode, using the persistent journey and no actor. Non-valid states keep context and hide the app CTA. Invalid codes keep the input editable, malformed codes are caught locally, and a network failure offers a retry that keeps the code.
